This is attribution and not access control, and the written file says so itself: anyone who can write the vault can rewrite the record, so it cannot keep anyone out. An agent's capabilities are attested by its publisher, and a revoked agent is refused

Partial
src/trust/agentManifest.js, src/trust/agentChain.js, src/trust/agentRevocation.js; tests/agent_manifests.test.js (27, against real Ed25519 keypairs)
Registered 2026-09-03 (v3 B5 T5-T7, ADR-0018 §1, §2, §5). Wired 2026-09-04 (ADR-0019 §7). For one day this was built and reached by nothing — authorizeAction() accepted an agentChain and no call site passed one, which is §82's defect, found by grepping our own work rather than shipped as a claim. The gateway now reads agentChain from the call and hands it to the gate, and tests/compositeprincipal.test.js drives a chain THROUGH the registry so the wiring cannot silently come apart. The chain is a CLAIM and is accepted unauthenticated, on purpose: every term in the effective set is an intersection, so naming more agents can only ever REMOVE, and the most permissive thing a caller can do is claim no chain at all. A liar can only lie themselves into a smaller set. It therefore buys attribution, not authorisation, and the record says so. The client NAME is the opposite and is now authenticated by a per-client token (ADR-0019 §7.2) — a name SELECTS a grant rather than adding a constraint, and before this any local process could claim to be claude-code and receive its capabilities, because the transport trusts localhost without a token.
